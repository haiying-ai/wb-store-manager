# WB 每日财务报表固定规则

批准日期：2026-09-17。适用于每日财务任务 wb-2，以及同一账本的日报、周报、月报和指定截止日报表。用户已确认本规则，日常运行无需重新确认。

本规则固化已发布的 `wb-owner-dashboard-v2.4` / `owner-dashboard-layout-v2`。本项目的列序、代运营费和回款定义，以本规则及当前批准的私有配置为准；通用技能中较早的示例不能覆盖这些已确认规则。

## 1. 每日入口与版本锁

- 运行 `python -m wb_manager finance daily --through yesterday --skip-workbook`。入口一次冻结上一完整莫斯科财务日，所有后续步骤使用同一截止日。
- 在任何 WB 来源请求前，校验 `config/finance/owner_report_template_release.json`、`config/finance/active_wb_periodic_reporting_standard.json` 中的版本、builder 路径和批准 SHA-256 与实际 builder 一致。生产必须为 `LOCKED`，不接受 `LEGACY_UNLOCKED`。
- 生成后、更新发布记录或归档前，再验同一指纹。计划任务不得修改 builder、服务、配置、测试、任务提示或布局来绕过失败。校验失败即停止当前运行；如有可信历史报表，按其原截止日返回并说明失败。
- 普通日 30 天、周一/月初 120 天修正窗口，结合持久缺口有界补采；各店独立入账。同一事件重放不新增，证据修订保留历史版本，不把每日累计快照相加。
- 先生成或复用主账本，再判断关闭周/月是否已被相同截止日覆盖；仅补最近一个未发布关闭周/月，不全历史重导。

## 2. 固定展示

固定 8 张表：汇总报告、老店汇总、新店汇总、老店订单、老店流水、新店订单、新店流水、周期对账。

三张汇总的 B—E 列固定为：**昨日 → 上周 → 上月 → 累计**，按 `yesterday / last_week / last_month / cumulative` 键绑定，不依赖传入数组位置。每列显示实际开始/截止日期；“昨日”相对报表截止日确定，历史报表不随机器当前日期漂移。四列有重叠，不能横向相加。

| 分组 | 固定核心字段（按行序） | 时间口径 |
| --- | --- | --- |
| 经营（8） | 销售额、退款额、净营业额、平台结算应收、采购成本、实际物流、其他费用、参考经营利润 | 各列期间发生额；利润按现金广告实耗口径 |
| 广告（3） | 已确认净计提、现金实耗、已确认预算结余 | 前两项为期间数；结余为各期末累计数 |
| 代运营（3） | 本期计提、本期实收、期末待付 | 前两项为期间数；待付为各期末累计数 |
| 资金（4） | 期末回款总额、期末累计提现到账、WB 余额快照、处理中提现 | 各列期末存量 |

- 三张汇总均为 18 个核心字段；金额及标题居右，G 列说明计算口径和缺口。
- 首页另列老店、新店重点摘要；各店独立展示经营结果、已确认广告预算、WB 余额、处理中提现和数据缺口。按店铺身份键匹配，不按列表位置匹配。
- 分店亏损、负广告预算、WB 负余额保留并突出；缺少分店实收分摊时明确标注，不因合并待付为零而声称两店各自结清。
- 第二利润口径、暂估广告结余、申请提现、促销金、退货储备及超额退货损失保留在明细或周期对账，不重新堆回首页。原始订单和流水证据保留。

## 3. 代运营费与已收款

- 执行 `config/finance/agency_withdrawal_fee_policy.json`：以每笔已确认银行提现到账为基数，使用批准费率，逐笔四舍五入到分，再按到账业务日期归属期间。
- 订单销售、提现申请、处理中金额及 WB 余额不计提代运营费。订单退款不自动冲销无关的已到账提现代运营费；真正的到账更正按原提现证据修订。
- 待付 = 截至各列期末累计计提 − 已登记累计实收 − 适用的已批准非现金结算调整。正数欠付，真实超付可为负数，不强制截为零。
- 实收与结算调整读取 `config/finance/owner_accounting_decisions.local.json`，按稳定事件 ID 幂等处理，并按各列截止日过滤。后日实收及调整不得进入更早的周/月报。
- 已登记的合并实收只算一次；未获分店分摊证据时保留未分摊状态，后续分摊不能再增加合并实收。
- 本次批准忽略的 0.01 元已作为关联原结算批次的专属非现金调整保存；不改写实收事实、不重复每日登记、不扩展为通用小额自动抹零。

## 4. 店铺回款

**各期末回款总额 = 截至该期末累计已确认提现到账 + 该期末之前最近的 WB 人民币账户余额快照。**

- 此项为含未提现余额的资金存量，不是期间到账流水。使用保留的余额历史快照计算各截止日，不以最新余额覆盖上周末/上月末。
- 保留负余额，注明快照观察日期及日内观察性质；来源缺失、过期或冲突需明确说明，不能填零或伪装成精确日终余额。
- 提现到账与 WB 余额均存在时显示已知回款合计；不因缺少独立入账流水而统一显示“待补汇款流水”。
- 处理中提现单列，不再次加进回款；其与账户余额的包含关系未获证实时不得猜测。
- 不从余额差制造 `receipts_received`，不把账簿余额或 WB 余额称为实时可提现额度。

## 5. 成本、利润与广告额度

- 人民币参考金额逐事件优先用正式金额，获准暂估只补对应缺口；不把正式与暂估两套金额相加，正式和暂估差额保留在明细。
- 参考经营利润扣除实际卖家现金广告、提现到账计提的代运营费和实际成本各一次；不同时扣广告计提与同一现金广告实耗。
- 退款使用原订单锁定事实，在退款期间冲回相关销售、结算应收和政策计提；确认可售退货后才冲回对应采购成本。已发生现金广告与不可退运费不随退款虚减。
- 广告展示正式已确认净计提及期末预算结余，扣真实自付消耗和适用历史共享退货物流，保留负数；促销金不计卖家现金成本，充值/划拨/消耗/周期扣款不重复记成本。
- daily 后运行 `python -m wb_manager finance funds-plan --through <同一已冻结日期>`，不带 report-id，读取共享账本生成 daily_funding，不重复抓全源或重建 Excel。
- 新增可划拨现金扣确认及未决现金划拨，不再重复扣实际现金消耗。暂估不进入确认额度；缺口和 `fundingAllowed` 必须如实保留。
- 日报仅更新、保存账面额度。资金执行另按用户明确授权核验实时同店账户和活动；不恢复已停止的主动续航检查或催批充值。

## 6. 每次交付核验

- 核验 8 表、三张汇总各 18 指标、四列键/日期、店铺绑定、期间数/期末数、公式错误及独立金额勾稽；保存回读并检查受影响视图。现有模板验证输出应包含 `summaryMetricCount=18`、指标行映射、金额及周期勾稽证据。
- 业务/映射/模板无变化，且业务指纹及 xlsx、report.json、verification.json 三项哈希一致，才可复用为 NOOP。模板变化不重复入账。
- 按私有 `runningAccounts.archiveRoot` 归档并回读 SHA-256，保留历史版本。辅助或归档失败不能抹掉仍有效的 workspace 报表，但须保留真实失败阶段。
- 来源不齐时显示已有事实和准确缺口，`PENDING_DATA` 不等于零交易。历史回退保留原 `dataThrough`，不可冒称本次截止日。
- memory 追加实际运行时间、截止日、模板版本、主文件/归档及哈希、资金文件及分店额度/缺口、失败和下次有界补采事项；不把历史待确认方案继续当作当前待办。

后续改版仅在用户授权的独立开发任务进行，完成自动与视觉资格验证后更新批准版本、指纹及本规则。日常任务不自行改版。
